PROJECT 4 · HYBRID-SEARCH TRIAGE

TriageLens

Hybrid-search intake triage with calibrated duplicate detection and PII scrubbing.

“Support teams drown in duplicates written in different words. Keyword search misses paraphrases, and vector search misses opaque error codes.

TriageLens runs both in one PostgreSQL query — full-text and pgvector HNSW, fused with Reciprocal Rank Fusion — scoped to the right category. The duplicate decision uses calibrated similarity thresholds, so it auto-merges only when it's sure and sends the grey zone to a human. Emails, phone numbers, UPI IDs, Aadhaar and API keys are scrubbed before any text reaches an LLM.”

Core Capabilities

One SQL query. Two retrievers. Safe intake.

TriageLens combines PostgreSQL's full-text search with pgvector 0.8 HNSW, fusing rankings with RRF and deciding with calibrated thresholds.

One query, two retrievers

A lexical GIN CTE and a semantic HNSW CTE fused via Reciprocal Rank Fusion (k=60) in a single SQL round trip.

Privacy-first PII scrubber

14 ordered regex rules with Luhn and Verhoeff checksums redact secrets, cards, Aadhaar, UPI, and phones before storage or LLMs.

Pinned error codes

Opaque identifiers like E_0X7F3A are invisible to embeddings (rank #16). Exact matches are pinned directly to #1.

Calibrated duplicate decisions

RRF ranks candidates, but cosine thresholds decide: ≥ 0.80 auto-merge, 0.70–0.80 human review, < 0.70 new ticket.

Category isolation

Search is scoped by category to prevent cross-category collisions (a crash bug never auto-merges into a feature request).

Iterative ANN scan

pgvector 0.8 strict_order continues walking the HNSW graph to avoid filter starvation caused by post-filtering.

Local embeddings

FastEmbed with BAAI/bge-small-en-v1.5 (384 dimensions) runs in-process on CPU with no network calls at runtime.

Per-session sandbox

Each visitor sees seed tickets plus their own created tickets and votes. Demo data automatically cleans up after 24 hours.

Architecture

Deterministic pipeline. Single SQL round trip.

Everything left of the decision is deterministic and testable. The LLM only suggests the category, which the user confirms.

Design Decisions

Trade-offs you must defend.

Eight core architectural choices behind the hybrid search, scoring, and data boundaries.

1. One query, two retrievers.

A lexical CTE (GIN index on generated tsvector: title and error code weighted A, description B) and a semantic CTE (HNSW on halfvec(384), cosine) are fused with RRF in a FULL OUTER JOIN. One round trip, one transaction, no second database to keep in sync.

2. OR plus minimum-should-match.

websearch_to_tsquery ANDs every word, so natural sentences match nothing; plain OR lets one shared word outrank the real match. TriageLens requires half the distinct query terms, capped at 4. On the paraphrase demo, OR-only pushed the true duplicate to #5; with the rule, it is #1. The term count runs only on rows the GIN index returns: written as one condition, it forced a scan of all 100,000 template tickets (500–840 ms); with a prefilter, 26–166 ms.

3. Exact identifiers are pinned, not ranked.

Error codes in the query (WORD_WORD_… pattern) are matched exactly against an indexed error_code column and pinned above fused results. An opaque code like E_0X7F3A is invisible to embeddings (rank 16 of 30).

4. RRF (k = 60) ranks; it doesn't decide.

Fusing ranks avoids the scale mismatch between ts_rank_cd and cosine. But an RRF score has no absolute meaning, so it cannot say “this is a duplicate”.

5. Calibrated thresholds decide.

Cosine to the best same-category candidate: ≥ 0.80 auto-merge, 0.70–0.80 human review, < 0.70 new; an exact error-code match lifts a candidate to at least review but never lowers the 0.80 bar for auto-merge. On the 31-ticket labeled set (in-sample): 21 of 23 duplicates auto-merged, 0 wrong merges, 4 sent to review (2 real, 2 lookalikes), 0 missed.

6. Category is part of the query.

The classifier suggests a category, the user confirms it, and search runs inside it. The best cross-category hit is shown as “related” but never acted on.

7. Iterative scans for filtered ANN.

HNSW collects about ef_search candidates and filters afterwards, so a filter can starve the result. pgvector 0.8's hnsw.iterative_scan = strict_order keeps walking until enough rows match, in exact distance order.

8. Honest about scale.

At 30 rows Postgres correctly picks a sequential scan (checked with EXPLAIN), and the UI shows the real plan. An “ANN lab” forces the index to demonstrate the filter trap; the benchmark measures HNSW at 100k rows.

Interactive Walkthrough

The 8-step live demo script.

Walk through every guarantee, reproducing each measured result on the seed database.

  1. 01

    Open the site (No login required)

    Observe
    Three search columns (Lexical, Semantic, Fused) and the telemetry strip: DB ms, embed ms, query plan, model name, and pgvector version.
    Why
    Transparency into what the database engine is actually executing.
  2. 02

    Preset “Opaque code: E_0X7F3A”

    Action
    Click the Opaque code chip.
    Observe
    Lexical pins BUG-109 #1 with an “exact code” badge; Semantic has it at #16; Fused puts it #1.
    Why
    “Embeddings can't see opaque IDs. Exact matching can.”
  3. 03

    Preset “Mobile avatar upload screen hangs”

    Action
    Click the Paraphrase chip.
    Observe
    Lexical is empty; Semantic and Fused rank BUG-102 #1 (cosine 0.66).
    Why
    “Zero shared words. Minimum-should-match keeps one-word noise matches from outranking it.”
  4. 04

    Preset “Android checkout dark mode”

    Action
    Click Category collision. Observe All, then switch to Bugs, then Features.
    Observe
    On All, FEAT-201 and BUG-105 tie. Under Bugs: BUG-105 #1. Under Features: FEAT-201 #1.
    Why
    “A crash bug must never be merged into a feature request.”
  5. 05

    Triage “Night mode for checkout on Android”

    Action
    Click Duplicate feature, review Preview, and click “Add vote”.
    Observe
    Decision is DUPLICATE of FEAT-201 (cosine 0.88). Vote counter bumps from 14 to 15.
    Why
    Features with high similarity accumulate community interest instead of cluttering the tracker.
  6. 06

    Triage “Dark mode for the web dashboard”

    Action
    Click Lookalike feature, review Preview, and click “Not a duplicate”.
    Observe
    Decision is REVIEW (closest is FEAT-201 at 0.75, but it is a distinct platform). New ticket is created.
    Why
    “That grey zone is why there are two thresholds.”
  7. 07

    Preset “PII + triage”

    Action
    Click PII + triage and preview.
    Observe
    8 redactions (email, phone, IP, UPI ID, PAN, card, 2 secrets). Order ref 2345 6789 0125 stays because its Verhoeff check fails.
    Why
    “Checksums keep random 12-digit numbers from being falsely redacted.”
  8. 08

    ANN lab & filter trap

    Action
    Click Filter trap. Compare iterative scan off vs strict_order.
    Observe
    Iterative scan off returns 1 row (starvation). strict_order returns 5 rows in exact distance order.
    Why
    “HNSW filters after collecting candidates; iterative scans keep walking until the filter is satisfied.”
